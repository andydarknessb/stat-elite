# Acceptance criteria in agent briefs

A criterion is a **result** the assigned actor can observe from inside its own sandbox, worded so a reader can tell red from green. The tell for a weak one: it names a **thing** (a suite, a job, a live session) where a result belongs. Each thing a criterion names has passed four lookups before the brief is posted:

1. **Exists.** The command, script, suite or fixture is in the tree today: `git grep` it, or read the `scripts` block of `package.json`. A rhetorical reference in the prose stays prose. StatElite has no `package.json` until the scaffold ticket merges, so until then a brief cannot name an npm script; a criterion on app code waits for the scaffold to land, or is blocked by it. For a test command, existence means the repo configures the runner it names, not merely that the binary sits in `node_modules/.bin`: a runner's transform and config can live in another package. Run the command the way CI runs it, and check that it selects the file the criterion names and no others. The working forms for a single file are whatever the repo's scripts document; `docs/schema.test.sql` is run with `psql -v ON_ERROR_STOP=1 -f docs/schema.test.sql` on a throwaway database.
2. **Producible.** The actor can make it from a branch and a PR. A required-check setting, a workflow's first green run on `integration`, a migration applied to a hosted database and an environment variable set on a host are the maintainer's actions, so the criterion stops at what the PR carries: the job definition, the migration file, the `Carve-out:` heading naming the post-merge action.
3. **Observable.** The actor can see the result without a production side effect. A live backend that holds real data is not an IC observation; the observable stand-ins are a unit test rendering from the new shape and an end-to-end spec on a mocked backend.
4. **Stated.** Every fact about the code that a criterion depends on is written down, with where it was read and when, in the ticket body under `## Premises`: one line per premise, `<path>: <claim> @<sha>`, the sha being the `integration` head you read the path at (full, or a prefix of seven or more), or the single word `none` when no criterion depends on the code. A line may be a `- ` list item and its path may be fenced in backticks; a line number belongs to the path (`path.js:71`). Nothing else goes in the section, and it lives in the body, never a comment. The format is the fleet's (its glossary, **Premise**): the fleet parses the section when a ticket is assigned, refuses a malformed one, and re-reads only the premises whose paths changed between their sha and the branch head, so a premise stated at cut time is the cheapest one to check later. The shape, with the sha left as a placeholder:

   ```
   ## Premises

   docs/plan.md:79: the planned stack is React, TypeScript and Vite @<sha>
   docs/schema.test.sql:3: a failed expectation raises an exception and stops the run @<sha>
   ```

**One ticket is one PR.** A ticket whose criteria need several pull requests to meet is several tickets. The lead assigns a ticket to one IC, which opens one PR against it, and a record that needs a second PR cannot be finished by the actor it was handed to. Cut the work at the PR boundary instead, with blocked-by edges between the pieces.

**Siblings that name the same path merge in order.** When two tickets cut from one spec state premises about the same path, the first to merge moves the code the second one's premise describes. Give them blocked-by edges in the order they will merge, so the second is not assigned until the first has landed and its premise can be re-read at the new head.

Write the criterion from what the lookups return: a command and its exit status, an assertion and the input that turns it red, a line the PR body must carry. Where the real check needs a human (a screen-reader pass, a two-browser session against a live backend), the brief says so and the ticket is `ready-for-human`, or the human half becomes its own child issue.

| Names a thing | Names a result |
|---|---|
| The schema self-check still passes. | `psql -v ON_ERROR_STOP=1 -f docs/schema.test.sql` on a throwaway database exits 0, and adding an update policy on `events` to a throwaway copy of `docs/schema.sql` stops it with "Events must not be editable". |
| The invitee sees the shared Athlete. | A unit test renders the Athlete list from the accept response shape and finds the Athlete's name; the test is red when the list drops Athletes a Member has joined. |

**Content vs. behaviour.** A criterion phrased over file contents is only safe when the string cannot legitimately appear in a comment, a test, or documentation. Otherwise phrase it over rendered output, or scope the paths explicitly and say which. A guard that must embody the thing it forbids (an absence assertion, a lint rule quoting the banned pattern, a fixture holding invalid input, or the document that explains the check) will break a naive content check, since explaining or forbidding a convention means writing an example of it; exclude those paths deliberately rather than discovering the collision later. Where a content check is right, state it in the form that survives: `git grep -nF` when the pattern contains regex metacharacters, a `':!<path>'` pathspec for the exclusions, and a positive control: a second `git grep` for a phrase that must match, proving the exclusion did not exclude everything.

**Which tests a mutation binds.** A red-tell criterion that names one mutation for a set of tests must say which tests in that set it binds. A presence assertion and an absence assertion are not sensitive to the same mutation: an absence reached by an earlier guard clause never reads the value the mutation changes, so it cannot go red under that mutation, and a criterion phrased over the whole set never moves together. Name the tests the mutation turns red, and state any exempt test separately with the reason.

**A literal a criterion hands to an artifact.** When a criterion tells the actor to put an exact string into a PR body, a commit message or a file, an obedient IC reproduces it exactly, wrapper and all, so whatever markup the brief sets the literal in becomes part of the artifact. Where the artifact is machine-read, the wrapper can change what the machine sees, and nothing goes red: the check the brief cares about is a different check, CI is green, and the wrong string ships. So the brief writes the literal the way the artifact must carry it, says where in the artifact it goes, and names a command that reads the string back the way the machine will. The closing keyword is the usual case: a `Closes #N` set in code style is the natural way to quote one in prose, but a keyword meant as a closing reference goes into the PR body unwrapped, on its own line. A brief that only quotes the convention in its own prose tells the IC to check the finished body rather than copy the quoted form.

A criterion that turns out unmeetable as written is recorded on the PR as unmet, with the reason, and the brief is corrected. A tick on it would tell the next reader that a check ran which never existed. The record states what was tried to make the criterion meetable, not only why it is not met: "unmeetable as written" is unfalsifiable by a reader, while "unmeetable, and here is the reformulation I attempted and why it fails" is checkable, and writing that sentence is what surfaces a reformulation that works.
